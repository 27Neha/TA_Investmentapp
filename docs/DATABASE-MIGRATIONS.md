# Database migrations

**Status:** `20261116000000_init` exists, was applied to an empty throwaway PostgreSQL 16 and checked against `schema.prisma` by automated tests.
**Not yet applied to any staging database** (no staging DB was provided to the build sandbox, and the owner's production/Supabase credentials were deliberately not used).

## Important: how this migration was produced
Prisma's schema-engine binary could not be downloaded in the build sandbox, so `migration.sql` was **written by hand** following Prisma's output conventions, not generated by `prisma migrate dev`. It is verified by `test/schema.int.spec.ts` (tables, columns, nullability, defaults, every `@unique`/`@@unique`/`@@index`, all 5 foreign keys with delete rules, all 5 enums) — but **you must also confirm zero drift with Prisma itself on your machine before applying to staging**:

```bash
cd apps/api
# 1. Drift check: should print "No difference detected"/exit 0. Needs an empty scratch (shadow) database.
npx prisma migrate diff \
  --from-migrations prisma/migrations \
  --to-schema-datamodel prisma/schema.prisma \
  --shadow-database-url "postgresql://USER:PASS@HOST:5432/shadow_scratch" --exit-code

# 2. Apply to STAGING ONLY (DIRECT_URL = non-pooled connection)
DATABASE_URL=... DIRECT_URL=... npx prisma migrate deploy
npx prisma migrate status

# 3. Seed (draft disclosures, feature flags all OFF, first admin from ADMIN_EMAIL/ADMIN_PASSWORD)
npm run seed
```
If step 1 reports differences, replace the hand-written file with the output of `npx prisma migrate dev --name init` and re-run the tests.

## Rollback
Prisma has no automatic down-migrations. For the init migration on a fresh staging DB, rollback = drop the schema (`DROP SCHEMA public CASCADE; CREATE SCHEMA public;`) — **staging only**. For later migrations, write an explicit reverse SQL file alongside each change and take a snapshot first.
